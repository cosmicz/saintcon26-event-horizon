#+startup: overview

* EVENT HORIZON

A 54-second demoscene production for the SAINTCON 2026 badge's 360×360 round
panel (RP2350): a chrome torus knot over plasma, a twisting tunnel, a terrain
flythrough and a particle rebuild into an end title, rendered natively on
both Cortex-M33 cores. It installs beside the badge's stock Wayfarer firmware
behind a boot menu, so the badge keeps working as a badge.

** Install on your badge

*You need your own stock backup.* This repository contains no firmware
image and none of the panel's register values. Those values belong to the
badge's stock firmware, so the build extracts them from a full flash backup
of your own badge (=device/tools/extract_panel_init.py=, static analysis
only; nothing is executed). Without the backup, the device images are not
built.

The build accepts only a backup whose firmware is byte-identical to the
Wayfarer v0.1 it was developed on (SHA-256 of flash =0x0–0x177000=:
=504a1d8f…35ad=) and whose remaining flash is erased. Whether every badge
shipped that way is unknown; a mismatch stops the build instead of producing
an image.

*At your own risk.* The dual-boot image has run on one badge; the
three-second menu update was also flashed and verified on October 30,
and the badge owner confirmed that it works
(details in [[file:device/dualboot/README.org][device/dualboot/README.org]]). Writing flash can brick a device,
so keep the backup safe; restoring it is documented but has not been run on
a badge.

*The EEPROM.* The badge keeps its saved state in an I2C EEPROM, which a
flash backup does not include: if it is lost, the backup will not bring it
back. The menu and demo never touch it, and the build audits both images
for I2C and EEPROM access (=device/dualboot/check.sh=). Stock, however,
reads buttons held during its start-up, and one combination resets that
saved state, so the boot menu never hands over to stock while a key is down.

The walkthrough below uses the same backup, build and flash commands used
for development. Run it from a POSIX shell, in order, and stop if any command
fails. The tested host is Apple Silicon macOS; other hosts are not verified.
Connect only the badge you intend to install on, using a USB data cable.

*** 1. Get the source and build tools

#+begin_src sh
git clone https://github.com/cosmicz/saintcon26-event-horizon.git
cd saintcon26-event-horizon
#+end_src

You need Git, Python 3, CMake, Ninja, picotool with USB support, the Pico SDK
and an =arm-none-eabi= GCC toolchain *including newlib*. The recorded device
build uses Pico SDK 2.3.1, picotool 2.3.1 and Arm GNU Toolchain 15.3.Rel2.
On macOS, Homebrew provides the host tools:

#+begin_src sh
brew install cmake ninja picotool
#+end_src

Download the =arm-none-eabi= archive for your host from
[[https://developer.arm.com/Tools%20and%20Software/GNU%20Toolchain][Arm GNU Toolchain]], check its published checksum, and extract it under
=~/.local/share/rp2350/=. Set
=PICO_TOOLCHAIN_PATH= to the extracted directory containing =bin/=; for the
tested Apple Silicon archive, =device/env.sh= defaults to
=~/.local/share/rp2350/arm-gnu-toolchain-15.3.rel2-darwin-arm64-arm-none-eabi=.
Install the SDK at the matching default location:

#+begin_src sh
mkdir -p "$HOME/.local/share/rp2350"
git clone --depth 1 --branch 2.3.1 https://github.com/raspberrypi/pico-sdk.git \
  "$HOME/.local/share/rp2350/pico-sdk-2.3.1"
. device/env.sh
"$PICO_TOOLCHAIN_PATH/bin/arm-none-eabi-gcc" --version
picotool version
#+end_src

If these tools are already installed elsewhere, export =PICO_SDK_PATH=,
=PICO_TOOLCHAIN_PATH= and =picotool_DIR= *before* sourcing =device/env.sh=.
=picotool_DIR= is the directory containing =picotoolConfig.cmake=.
[[file:device/README.org][The toolchain notes]] describe the tested setup. SDK submodules are not
needed for this build.

*** 2. Back up your badge

This walkthrough starts with an unmodified badge running the original
Wayfarer firmware. A new dump of an already modified badge is not a stock
backup and will be refused by the build; keep the original backup for any
later update or rollback.
The =-f= option asks compatible running firmware to reboot into BOOTSEL;
if picotool cannot reach the badge, stop and follow the badge maker's
BOOTSEL instructions rather than proceeding without a backup.

Create a fresh directory outside the checkout so a later run cannot replace
your original backup. Keep this shell open: the remaining commands use the
same =badge_install_dir= variable.

#+begin_src sh
umask 077
badge_install_dir=$(mktemp -d "$HOME/event-horizon-install.XXXXXX")
picotool save -a -v -f "$badge_install_dir/stock-fullflash.bin" -t bin && \
  test "$(wc -c < "$badge_install_dir/stock-fullflash.bin")" -eq 16777216 && \
  shasum -a 256 "$badge_install_dir/stock-fullflash.bin" > "$badge_install_dir/stock-fullflash.sha256" && \
  chmod 400 "$badge_install_dir/stock-fullflash.bin"
#+end_src

The backup must be exactly *16,777,216 bytes*, and picotool's save verification
must pass. Make another safe copy of the backup and its checksum file before
continuing. Keep both, and the generated image below, out of Git and public
uploads: they contain stock firmware. This flash backup does not include
the EEPROM described above.

*** 3. Build, audit and pack

This step runs on the computer; it does not access the badge.

#+begin_src sh
sh device/dualboot/check.sh "$badge_install_dir/stock-fullflash.bin" "$badge_install_dir/image"
#+end_src

The script extracts the panel initialization from your backup, builds the
menu and demo, runs the EEPROM/flash and source-pin audits, checks that its
negative witnesses fail as expected, and packs the image with your relocated
stock firmware. It must finish successfully. A stock-version mismatch or
failed audit is a stop, not a check to bypass.

The result is =$badge_install_dir/image/dualboot.bin=, with slot files and a
=manifest.json= recording their hashes. Keep the entire output directory.

*** 4. Install and boot

*The next command writes the badge's flash.* Start with Wayfarer running;
if the demo is running, power-cycle and let the menu boot Wayfarer. Recheck
your original backup, then install the packed binary at the explicit address:

#+begin_src sh
shasum -a 256 -c "$badge_install_dir/stock-fullflash.sha256" && \
  picotool load -v -x "$badge_install_dir/image/dualboot.bin" -t bin -o 0x10000000 -f
#+end_src

Wait for write verification to pass and the badge to reboot. Its three-second
menu defaults to Wayfarer; press RIGHT to choose EVENT HORIZON and press the
stick to start it. Holding RIGHT during power-on starts the demo directly.
To get back to the badge, power-cycle and let Wayfarer boot. Do not install
by dragging a UF2 onto the USB drive; the partition layout matters.

*** Restore the original firmware

Keep the full backup for rollback. From Wayfarer (or the badge's BOOTSEL
mode), writing it back at the same address removes the dual-boot layout:

#+begin_src sh
shasum -a 256 -c "$badge_install_dir/stock-fullflash.sha256" && \
  picotool load -v -x "$badge_install_dir/stock-fullflash.bin" -t bin -o 0x10000000 -f
#+end_src

*Restoring the backup has not been exercised on hardware.* It restores flash,
not EEPROM state. If you reopen your shell, first set =badge_install_dir= to
the original backup directory; do not create a new backup of the modified
badge and mistake it for the original.

Layout, safety argument and hardware observations:
[[file:device/dualboot/README.org][device/dualboot/README.org]].

** On the badge

| At power-on | Result |
|-------------+--------|
| Hold RIGHT | The demo starts at once |
| Nothing held | A menu shows Wayfarer (left) and the demo (right) for 3 s, then boots the highlighted one (Wayfarer by default) |

In the menu, LEFT and RIGHT choose and restart the countdown; pressing the
stick confirms. In the demo, the D-pad steers the camera, centre resets it,
A cycles the palette and B toggles a wireframe torus.

** The renderer

| Scene | Time | Technique |
|-------+------+-----------|
| Chrome torus knot over plasma | 0–14 s | Fixed-point plasma; (2,3) knot tube 160×16, banded z-buffer, 128² sphere env map; dive and white-out exit |
| Twisting textured tunnel | 14–26 s | Mirrored quadrant angle/depth LUT (1024 steps) with camera offset; 128² bevelled texture; depth shade |
| Terrain flythrough | 26–42 s | 256² height/colour maps, front-to-back column march, terrain-following camera, fog, rising sun |
| Particle rebuild | 42–54 s | 8,192 particles seeded from the last terrain frame stream back, with trails, into the end title |

The portable core (=src/core=) renders RGB565 at the panel's native
resolution with a two-core frame plan (8 parts, 1–2 passes). Its RAM peak is
85.6% of the RP2350's SRAM. The same core drives a desktop preview and
the device build.

** Desktop preview and tests

Requirements: CMake ≥ 3.20, a C11 compiler, Python 3. SDL2 is optional and
only needed for the interactive window. Developed on macOS 15 (Apple M2 Max,
AppleClang 17); the device toolchain is described in [[file:device/README.org][device/README.org]].

#+begin_src sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
(cd build && ctest --output-on-failure)
python3 tools/mutation_check.py           # every targeted mutant must fail a test

# ASan + UBSan
cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DEH_SANITIZE=ON
cmake --build build-asan -j && ctest --test-dir build-asan --output-on-failure

# ThreadSanitizer over the two-thread pool
cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug -DEH_TSAN=ON -DEH_PREVIEW=OFF
cmake --build build-tsan -j && ctest --test-dir build-tsan --output-on-failure

# Lower a quality knob (see include/eh/eh_config.h), e.g. trails off
cmake -S . -B build-knob -DCMAKE_BUILD_TYPE=Release -DEH_DEFINES="EH_PARTICLE_TRAILS=0"
#+end_src

Interactive window: =./build/eh_preview [--scale N] [--start MS] [--threads 1|2]=

| Key | Badge control |
|-----+---------------|
| Arrows | D-pad (camera yaw/pitch) |
| Enter / Space | D-pad centre (reset camera) |
| Z | A — next palette |
| X | B — wireframe torus |
| P / R / [ ] / 1–4 | pause / restart / seek ∓5 s / jump to scene |

Headless:

#+begin_src sh
./build/eh_cli frames --out out/frames                 # PPM per scene midpoint, JSON line per frame
./build/eh_cli frames --out out/f --at 5000,9000 --hold RIGHT:3000-5000
./build/eh_cli bench demo [--threads 1|2]
./build/eh_cli memory                                  # calculated + painted high-water
#+end_src

=frames= plays from t = 0 in 30 fps steps, so =--hold BTN:FROM-TO= acts like
a held button (=UP DOWN LEFT RIGHT CENTER A B=). Each PPM is the full 440×440
presentation: panel plus LED ring.
